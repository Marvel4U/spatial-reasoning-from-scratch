**Key observations**
- TRL now has a genuinely usable tool loop (`tools`, `environment_factory`, image-returning tools, tool-call metrics) and the only documented *single-GPU* vLLM colocate recipe. Its docs are silent on whether tool-result tokens are masked from the loss — **verify in `grpo_trainer.py` before trusting** (verl explicitly does delta-tokenization masking).
- ART is the most ergonomic "agent-as-rollout" design, but no VLM support — could still be a design reference for a hand-typed loop.
- verl is the reference implementation for everything in the literature (DeepEyes, Qwen3-VL's own tool-RL pipeline, LinkedIn's retrospective) but brings Ray, FSDP configs and multi-GPU assumptions.
- The LinkedIn GPT-OSS post (Jan 2026, verl) documents the real-world pitfalls: train/inference logprob mismatch (TIS/MIS correction — TRL exposes `vllm_importance_sampling_correction`), MoE routing nondeterminism (avoid MoE policies for RL on one GPU), memory bloat.

## 3. Parallel / multi-tool calling

**State of play**
- Frontier models issue many calls per turn routinely; BFCL v4 scores "parallel" and "parallel-multiple" categories separately, and this is exactly where small models drop off ([BFCL](https://gorilla.cs.berkeley.edu/leaderboard.html), [Spheron overview](https://www.spheron.network/blog/tool-calling-benchmarks-bfcl-tau-bench-latency-optimization/)). BFCL v4 leaderboard top is Qwen3.7-Max at 0.75 (Sep 2026); I could not retrieve per-category numbers for 4B/8B models — pull the CSV yourself.
- τ²-bench (v1.0.1, Jul 2026) is the multi-turn tool-use standard; small-model numbers are low but trainable: Firefly-RL (GRPO on a 4B model, verified data from 240 real MCP servers) lifts Qwen3-4B Retail 0.49→0.63, Airline 0.37→0.53 ([Firefly](https://arxiv.org/abs/2605.17558)).
- **Width vs depth**: W&D (Feb 2026) shows intrinsic parallel tool calling in a single step reduces turns and beats deeper sequential search on BrowseComp (GPT-5, no training details) ([W&D](https://arxiv.org/abs/2602.07359)).
- **Directly relevant precedent — ParaVT / PARA-GRPO (May 2026)**: RL-trains a Qwen3-VL-based video agent to dispatch *multiple crops in one turn*. Identifies the "tool prior paradox": pretrained tool priors enable exploration but collapse output format and create a *skip-tool reward shortcut*; fixes = format reward only at structural tokens + per-prompt budget randomization so tool use has measurable advantage. Format compliance 0.13→0.64 ([ParaVT](https://arxiv.org/abs/2605.20342)). This is the closest published analogue to "issue ~10 map-query tools in one turn".
- Other 2025–26 training work: Nemotron-Tool-N1 (RL for tool reasoning, ToolACE data with parallel calls) ([paper](https://arxiv.org/pdf/2505.00024)); Hammer (function masking for on-device models) ([paper](https://arxiv.org/pdf/2410.04587)); ParallelSearch / RAG-R1 / Hybrid-DeepSearcher (RL to decompose queries for parallel execution) ([survey context](https://arxiv.org/pdf/2601.19568)); CacheRL (cached rollouts for multi-turn tool agents on Qwen3-4B-Thinking) ([paper](https://arxiv.org/pdf/2606.14179)); RC-GRPO (reward-conditioned GRPO for multi-turn tool agents) ([paper](https://arxiv.org/pdf/2602.03025)); IAPO (Qwen2.5-VL-3B tool use, attribution-aligned rewards instead of brittle exact-match) ([paper](https://arxiv.org/abs/2606.11652)); "On Effectiveness and Efficiency of Agentic Tool-calling and RL Training" (ICML'26: results are highly sensitive to seeds/system prompt/history handling; many prompts yield zero learning signal → filter) ([paper](https://arxiv.org/pdf/2606.00135)).
- Practical: Qwen's chat template supports multiple `<tool_call>` blocks per assistant message; TRL's tool loop executes all calls in a message before the next turn (per docs) — **verify parallel-call execution path in TRL** since docs only show single-call examples. vLLM's `hermes` tool parser handles multiple calls.

**Takeaway**: no off-the-shelf "teach a 4B VLM to fire 10 parallel tools" recipe exists; ParaVT + Firefly + Qwen3-VL's own SFT→tool-RL pipeline (10k cold-start grounding SFT → tool-integrated RL → self-distill 120k → repeat) are the closest blueprints.

## 5. Recommendation shortlist

**Option A — TRL `GRPOTrainer` (+ optional Unsloth acceleration), hand-written tool/env layer.** *Recommended default.*
- Pros: only framework with a documented single-GPU vLLM colocate path; `tools=[fn]` + `environment_factory` + image-returning tools map directly onto your map-world tools; VLM support incl. Qwen3-VL/Gemma 4; TIS/MIS mismatch correction built in; SFTTrainer for the agentic-SFT stage in the same stack; pure-PyTorch enough that Marvin can read and own `grpo_trainer.py`'s loop.
- Cons: tool-result loss-masking and parallel-call execution semantics need verification in source; Qwen3.5's hybrid attention may lag in vLLM/transformers kernels (check before committing; Qwen3-VL-4B/8B is the safe base); AsyncGRPO/env features are young (v1.8–1.13, Jul–Sep 2026).
- 3060 tier: Unsloth GRPO on Qwen3-VL-2B/4B for smoke; 96GB tier: TRL colocate, LoRA or full FT on 4B–9B.

**Option B — verl (`tool_agent` loop) on the Hetzner box.**
- Pros: the reference implementation for DeepEyes/Qwen3-VL/LinkedIn-style tool-RL; explicit tool-token masking; async agent loop; Qwen3-VL/3.5 scripts exist; best interview credibility ("I ran the industry stack").
- Cons: Ray + FSDP + YAML sprawl; single-GPU is possible but examples assume ≥2 GPUs; LoRA on Qwen3-VL-8B reported slow; less of the loop is "typed by hand"; heavier to debug on the 3060.
- Use as a **cross-check** (reproduce one run) rather than the primary stack, or if TRL's tool loop proves too immature for 10-call turns.

**Option C — Own minimal GRPO loop (ART-style design) on vLLM + PEFT, using TRL only for SFT.**
- Pros: maximum ownership/defensibility; you control parallel-call parsing, masking, per-tool rewards and step-level credit (GiGPO/ParaVT ideas); vLLM native server + NCCL weight sync (as TRL v1.11 does) is now a documented pattern to copy.
- Cons: highest engineering risk on a shared-evening timeline; you re-implement colocate memory management, importance-sampling correction and multimodal weight sync yourself.
- Fits the authorship rule best; realistic only if Stage 1 (SFT) ships first and RL scope stays narrow.

**Base-model call to make in OPEN_DECISIONS**: Qwen3.5-4B/9B (newest, native multimodal agent, Apache, but hybrid-attention kernel maturity risk) vs Qwen3-VL-4B/8B (broadest framework support, tool-RL-trained upstream, 0–1000 grounding coords) vs Gemma 4 E4B (multimodal function calling + JSON boxes, Apache). Avoid MoE policies for on-GPU RL (routing nondeterminism).
