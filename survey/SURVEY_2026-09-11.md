## 1. The competition: what we will be measured against

**Public eval targets (the ones a reviewer will ask about):**

| Benchmark | Why it matters to us | Status |
|---|---|---|
| **MapEval** (ICML 2025) — Textual / API / Visual splits, 700 MCQ, real Google-Maps data | The anchor. MapEval-API = tool-using map QA; MapEval-Visual = map-image QA. No model above 67%; best open VLM ~60% on Visual. | Code + data public. MCQ only, no zoom/measure tools. |
| **MapReason-OSM** (Jun 2026) — 12k self-rendered OSM panels, 10 US downtowns, two zooms, 12 tasks, graph-verifiable answers | Closest benchmark to our setup: rendered OSM, verifiable answers, multi-zoom. Frontier VLMs score 0.19–0.39 on the hard tasks (facility siting, POI routing) with no tools. | CC BY 4.0, code + data. Eval only, nobody trains on it. |
| CartoMapQA, MapVerse, MapBench, FRIEDA | Real-map VQA OOD evals. FRIEDA: frontier ~38% vs humans 85% on metric/directional map reasoning. | Mostly open. |
| GeoBenchX, GeoAgentBench, GeoNatureAgent | Text-only geo tool-calling benchmarks; useful for tool-trajectory scoring conventions. | Mixed. |

**Existing agents on the same benchmarks:** MapAgent (EACL 2026, MapEval authors) and Spatial-Agent (Jan 2026) are the current SOTA scaffolds on MapEval-API. Both *prompt* frontier models. No paper reports a 3–8B model *trained* for map QA and evaluated on MapEval or MapReason-OSM. That is the clean claim slot.

**Closest projects on the training axis (must cite, must read in full before finalising DESIGN):**

- **PERIA** (Jun 2026): Qwen3-8B, tool-augmented spatial reasoning incl. map tasks, synthesized trajectories + RL. Generic image tools (crop, trace, verify), no geo data layers, no real-city world state.
- **Thinking with Map** (AMap, Jan 2026): Qwen3-VL-30B-A3B, six map tools incl. zoom, GRPO from base, verifiable distance reward. But the task is photo geolocation; the map is a tool *output*, not the input.
- **OpenEarthAgent** (ECCV 2026): agentic SFT on 14.5k validated geo-tool trajectories with deterministic replay, satellite imagery. Fully open. Their trajectory-validation pipeline is worth copying.
- SpatialLadder / SpatialThinker (3B–7B, curriculum SFT→RLVR, synthetic data) remain the template at our scale; no direct 2026 successors found.
- Reward-design references: Smooth Operator (continuous numerical rewards for distances), Pigeon (programmatic spatial assertions as dense rewards), DeepEyes (zoom-tool RL; gates tool reward on tool actually used).

**Where the gap is (my reading of raw/01):** nobody trains a small model that (a) takes a map image as input, (b) interleaves visual actions (zoom) with data-layer queries (hours, elevation, transit), (c) verifies against the underlying world state, and (d) reports on MapEval / MapReason-OSM. Each piece exists in isolation. The project's thesis survives the survey, narrower than the docs assumed but intact. Even a negative result on the public splits is portfolio-grade if the eval is honest.

## 2. Training tooling (raw/02)

- **HF TRL** (v1.13, Sep 2026) is the only stack with a documented single-GPU path: multi-turn tool loop (`tools=`, `environment_factory`), tools may return images into the next VLM turn, vLLM colocate on one GPU, importance-sampling correction for train/infer mismatch. Two things to verify in source before trusting: whether tool-result tokens are masked from the loss, and whether several tool calls in one assistant message are all executed (docs only show single calls).
- **verl** is the industry reference (DeepEyes, Qwen3-VL's own tool-RL, LinkedIn retrospective) with explicit tool-token masking, but assumes Ray + multi-GPU. Good as a cross-check, not the primary stack.
- **Unsloth** is the fastest path for the 3060 smoke tier (Qwen3-VL GRPO on tiny VRAM) but its vLLM path cannot train vision layers, and it is heavy monkey-patching, i.e. weak on the "typed by hand" axis.
- **ART** (OpenPipe) has the nicest agent-as-rollout design but no VLM support. Design reference only.
- **Parallel tool calling at scale:** no off-the-shelf recipe teaches a 4B VLM to fire ~10 tools in one turn. Closest: ParaVT / PARA-GRPO (May 2026), which RL-trains multi-crop dispatch in one turn and documents the "tool prior paradox" (format collapse, skip-tool reward shortcut) and its fixes (format reward only at structural tokens, per-prompt budget randomisation). Firefly-RL shows GRPO lifting Qwen3-4B on τ²-bench. Qwen chat templates support multiple `<tool_call>` blocks per message. Marvin's ambition is feasible but will need its own reward design; it is not a solved problem to import.
- **Base models (Sept 2026):** Qwen3.5-4B/9B (newest, "native multimodal agents", Apache; hybrid attention → kernel maturity risk in vLLM/transformers), Qwen3-VL-4B/8B (broadest framework support, upstream tool-RL trained, 0–1000 grounding coords, safe fallback), Gemma 4 E4B (multimodal function calling, JSON boxes, Apache). Molmo 2 has best-in-class pointing but no native tool format. Avoid MoE policies for on-GPU RL (routing nondeterminism).
- **Recommendation from raw/02:** TRL as the primary stack with a hand-written tool/env layer; verl for one cross-check run; an own minimal loop only if RL scope stays narrow after Stage 1 ships. I agree with this ordering.

## 3. Open data landscape (raw/03, raw/04)

**Layer-by-layer verdict across all cities studied:**

| Layer | State | Consequence |
|---|---|---|
| Base vector (OSM, Overture) | Universal | Fine. Overture `places` is CDLA-Permissive and contains no OSM data — the licence-clean POI spine. |
| Buildings + heights (LoD2) | NL best (3DBAG, CC BY, bbox CityJSON API); Vienna, Zurich strong; Paris good (APUR); **Barcelona has no open LoD1/LoD2**, must derive from ICGC LiDAR (2008–11); London OS heights are non-redistributable, derive from EA LiDAR; NYC 3D is 2014-vintage | Height-dependent layers are easy in NL/Vienna, self-built in BCN/London. |
| Sidewalk polygons / widths | Paris (trottoirs emprises), NL (BGT `wegdeel`/`voetpad`), Vienna (FMZK), City of London only (2.9 km²) | Directly enables "terrace fits here" tasks in those cities. |
| Sun / shadow | **Computed everywhere** from heights + solar position; published products are roof-potential only | This is good: verifiable by construction, and a natural tool + reward. |
| Noise (EU END maps) | Barcelona best in survey (per-facade, 4 vintages, CC BY); Amsterdam, Paris (Bruitparif), Vienna all good; **NYC has none** (311 complaints are a confounded proxy) | Excellent "information not in the pixels" layer for EU cities. |
| Opening hours | **Universally weak**; no municipal portal publishes shop hours; OSM `opening_hours` coverage unmeasured. Paris publishes daily-synced hours for parks/pools/libraries/museums only | Top item to measure before committing to time-aware questions. |
| Commercial register / terraces | Barcelona (cens d'activitats + terrace licences), Paris (BDCOM door-to-door retail census + ~19k terrace permits) unique | Both cities can ground the terrace-style P3 tasks in official data. |
| Transit GTFS | NL key-free national (OVapi, CC0), IDFM, TfL, MTA fine; TMB needs an API key → use Transitland/Mobility Database archives for dated snapshots | Snapshot with date; frequencies computable from static GTFS. |
| Footfall | Amsterdam CMSA (public), Melbourne (~99 sensors hourly since 2009, still live); Paris none, London ended 2020, NYC sparse | Melbourne is the only city where "foot traffic" is measured, not inferred. |
| Elevation | AHN5 0.5 m (NL), IGN LiDAR HD 50 cm, EA 1 m, NYC 1-ft, ICGC 2 m | All fine. |
| Population grid | CBS 100 m (NL), INSEE 200 m, census | Fine. |

**City verdicts:**

- **Amsterdam / Netherlands:** the strongest geometry stack anywhere (3DBAG + AHN5 + BGT sidewalks + CC0 GTFS + footfall + 100 m population grid). Canals make Euclidean vs network distance diverge sharply — a genuinely useful failure mode for tasks. Caveat: maps.amsterdam.nl uses bespoke terms and does not keep historical datasets, so snapshot early and record dates. No commercial register (KvK is closed).
- **Barcelona:** best noise data in the survey, unique commercial census and terrace licences, cleanly CC BY 4.0 almost everywhere, Eixample grid is friendly for orientation tasks. Structural gap: no open 3D buildings, so heights (and therefore shadow) must be derived from older LiDAR or photogrammetry. Marvin can ground-truth in person.
- **Paris:** the best of the three "big" cities by a wide margin (sidewalk polygons, tree-aware solar cadastre, Bruitparif noise, Airparif 10 m air quality, BDCOM, terrace permits, 50 cm LiDAR). ODbL share-alike on Ville de Paris layers needs a licensing decision.
- **London:** OS licensing blocks the official building/road layers. Choose the **City of London** as the district: it is the only area with open pavement widths, and TfL's Cycling Infrastructure Database (every street surveyed) is a standout.
- **New York:** richest attributes (MapPLUTO, 6-inch planimetrics, 1-ft LiDAR) but no noise map, vintage-mismatched 3D stack, and no formal open licence (Terms of Use only).
- **Additional candidates:** Vienna rated best overall (sidewalk polygons, far-field-shadowed solar cadastre, bbox downloader for every layer, one CC BY 4.0 string). Zurich and Helsinki strong. Melbourne only for footfall. Rotterdam inherits the NL stack.

**Licensing needs deliberate design before ingestion.** ODbL (OSM, Overture base/buildings/transport, Ville de Paris) is share-alike on derivative databases, which plausibly includes a generated QA corpus. Mapillary is CC BY-SA. The permissive spine is municipal CC BY / Licence Ouverte / OGL layers + Overture `places` (CDLA-Permissive) + national mapping agencies + census. Every snapshot should carry a per-layer vintage manifest, since each is a composite of capture dates.

## 4. What this changes in the project docs

1. **The world substrate question is answered in principle:** real-city frozen snapshots, not procedural worlds. Verifiers and tools read the same local datastore. "Synthetic" = rendered map images + generated tasks. The Stage 3 "synthetic → real OSM" story becomes "held-out city" generalisation instead, which is cleaner.
2. **Public eval targets exist and should be in the eval protocol from day one:** MapEval-API, MapEval-Visual, MapReason-OSM (hard subset), with CartoMapQA/FRIEDA as OOD sanity checks. Our own held-out-city eval remains the headline.
3. **Sun/shadow and noise are the model P2 layers:** shadow is computed from heights (verifiable by construction), noise is measured (EU END). Opening hours is *not* a safe P2 layer until OSM coverage is measured per city.
4. **Tool API v1 gets a new constraint:** if the ~10-calls-per-turn ambition is real, the format must allow multiple tool calls per assistant message from the start (Qwen template supports it), and the reward design must anticipate the ParaVT failure modes.
5. **Base-model shortlist for OPEN_DECISIONS (c):** Qwen3.5-4B/9B vs Qwen3-VL-4B/8B vs Gemma 4 E4B.
6. **Prior-work section for the README:** PERIA, Thinking with Map, OpenEarthAgent, MapAgent, MapReason-OSM, SpatialLadder must all be cited and positioned.
